## Root cause

Two defects in vendored memoryjs (vendor/memoryjs-3.5.1-patched):
1. process::openProcess always opened handles with PROCESS_QUERY_INFORMATION|PROCESS_VM_READ
   only — no PROCESS_VM_WRITE/PROCESS_VM_OPERATION — so every write was structurally impossible.
2. writeMemory (memory.h) discarded WriteProcessMemory's return value; the JS binding
   (memoryjs.cc) never checked or propagated failure. Writes silently no-op'd and reported success.
See native-write-root-cause.md for full detail.

## Fix

- process.h/process.cc: openProcess(pid, errorMessage, requestWriteAccess=false) — write rights
  granted only when explicitly requested; default unchanged; never PROCESS_ALL_ACCESS.
- memoryjs.cc: openProcess() binding accepts an optional boolean 2nd argument (backward
  compatible) to request a write-capable handle.
- memory.h: all writeMemory overloads now return bool (success + full byte count written) and an
  out-param Win32 error code.
- memoryjs.cc: writeMemory()/writeBuffer() bindings check the result and throw
  `write_failed:<code>` on any failure or short write — no memory values/addresses/tokens/paths
  in the error.
- native-memory-driver.ts: openProcess(pid) now requests write access (mem.openProcess(pid, true)).
See native-access-rights-model.md and native-error-propagation.md for full detail.
