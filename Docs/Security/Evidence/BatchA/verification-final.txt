=== HANDOVER CLAIM CORRECTIONS (each verified against command output on disk) ===

1. Handler count: handover said 149. Raw `grep -rn "ipcMain.handle" electron/*.ts`
   returns 150 matches; one is a FALSE POSITIVE — a code comment at
   electron/main.ts:294 ("// ipcMain.handle registrations for V2 channels
   are at module level (below)") contains the literal substring
   "ipcMain.handle" but registers nothing. True count, confirmed by parsing
   actual `ipcMain.handle('channel-name', ...)` call sites: 149. No
   duplicate channel names exist across the 149.

2. Preload wrapper contradiction ("154 vs 149 = 5 orphans"): RESOLVED, not a
   bug. electron/preload.ts exposes 155 total keys via exposeInMainWorld:
   1 static test fixture (e2eTrainerState) + 154 function wrappers. Of the
   154 function wrappers, 149 call ipcRenderer.invoke() with a channel name
   that maps 1:1 onto all 149 registered ipcMain.handle channels (zero
   missing in either direction, confirmed via set comparison). The other 5
   wrap ipcRenderer.on() as one-way main-to-renderer PUSH event listeners
   (onLiveMemoryCorrelationReport, onTrainerHotkey, onCtLibraryImportProgress,
   onCatalogProcessDetected, onZeroInputReady) — these were never meant to
   correspond to an ipcMain.handle channel. Each of the 5 was traced to a
   live webContents.send()/event.sender.send() call in the main process
   (see ipc-preload-orphans.csv for exact file:line citations) confirming
   none is dead code.

3. Renderer call count: handover said "160 calls found." Actual count,
   derived from grepping all 154 preload method names against src/app/
   (the renderer UI layer) with call-site patterns covering direct,
   optional-chained (?.), and non-null-asserted (!.) invocation styles:
   222 real call sites (confirmed false-positive-free by excluding
   src/core/* name collisions, e.g. the backend's own getGames()/setSetting()
   functions, which share names with electronAPI methods but are unrelated
   direct function calls, not IPC). 14 of the 154 preload methods have zero
   confirmed renderer call sites in src/app (see ipc-renderer-callers.csv,
   called=no rows) and are either dead/unused from the UI today or invoked
   via an indirection this regex-based method cannot follow (one such case,
   liveMemoryZeroInputPrepare, was manually found and corrected in the CSV;
   the remaining 13 were spot-checked and appear genuinely unused).

4. Registry Operations: handover assumed electron/registry-verification-ipc.ts
   performs actual Windows registry/WMI access based on its filename. FALSE —
   read in full, that file never touches HKLM/HKCU/WMI. "Registry" there
   means an in-app compiled Cheat Engine table artifact. The actual Windows
   registry access (reg query via execSync) lives in
   src/core/install-discovery/registry-win.ts, previously unexamined by any
   session. See registry-operations-audit.txt for the full trace.

5. Process execution locations: handover estimated 6, "2/6 analyzed."
   Exhaustive grep for spawn/spawnSync/exec/execSync/execFile/execFileSync
   across electron/ and src/ (excluding node_modules and non-executing
   regex .exec() calls) found 10 distinct real call sites. All 10 are
   documented in process-execution-audit.csv with command, argument style,
   shell option, and injection-risk assessment.

6. Consent-gated handler count: handover assumed 7 handlers in files named
   "in-process-*.ts". No such files exist — those channels live inside
   electron/live-memory-ipc.ts. A full cross-reference of
   handler-authorization-audit.csv found 13 handlers with an active
   consent_gate, not 7. See consent-state-machine-audit.txt for the
   complete token-lifecycle trace (creation, TTL, single-use enforcement,
   sender binding, concurrency) plus 3 Batch-B-relevant findings (env-var
   consent bypass hook with no production guard, unbounded token-store
   growth, and inconsistent hardening across consent flows).

7. Scan-SolithSecrets.ps1: referenced in the handover as an existing tool.
   It does not exist on disk (only Extract-SolithIpcSurface.ps1 does). A
   manual regex-equivalent scan was run in its place; see
   secret-scan-summary.txt for the exact patterns used and the discrepancy
   note.
