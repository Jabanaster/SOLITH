===== FINDING DISPOSITION (CORRECTED) =====

live-memory-rollback:
  PARTIALLY FIXED. The arbitrary-manifest write primitive (the original,
  most severe defect — a renderer could supply any address/value/dataType
  under the guise of "rollback") is closed: rollback now takes only a
  proposalId, resolved server-side against a ledger of writes this session
  actually confirmed. CONFIRMED STILL ABSENT: an expected-current-value
  (compare-and-swap) check before the restore write, a fresh consent
  requirement for the rollback operation itself, and any expiration/TTL on
  ledger entries. See finding-revalidation-v2.md section 2 for the full
  binding matrix and the 2 new "KNOWN GAP" tests that prove these gaps
  empirically rather than asserting them.

live-memory-freeze-start:
  PARTIALLY FIXED. Session-level bound enforcement, a 6-hour duration cap,
  and renderer-window-destroy cleanup were added. CONFIRMED STILL ABSENT,
  and NOT merely a deferred nice-to-have: a per-operation consent token,
  which Batch A explicitly named as the defining characteristic of this
  handler's HIGH risk rating. Also newly identified this pass: no
  survives-reload protection, no per-process/global concurrency limit
  (two Solith windows share the same preload/API surface and could each
  independently freeze the same process), and no feature-flag re-check
  during an active freeze's tick loop. See finding-revalidation-v2.md
  sections 4-5.

registry-run-readonly-verification:
  PARTIALLY FIXED. A concrete prior defect (hardcoded `selectedByUser: true`
  regardless of renderer input) is closed — the renderer must now
  explicitly send `userSelectedProcess: true` or the schema rejects the
  call. This is a self-attestation, not server-verified proof of user
  action, and was mischaracterized as stronger than that in the original
  version of this evidence. Sender validation remains liveness-only
  (`event.sender.isDestroyed()`), consistent with — not worse than — every
  other one of the 149 handlers audited in Batch A; no handler in this
  codebase does BrowserWindow/frame/origin validation, which is a systemic
  characteristic, not specific to this handler. Read-only enforcement and
  the non-shell (worker_threads, not child_process) execution model were
  re-verified this pass with exact file/function citations proving no
  mutation-capable API is reachable. See finding-revalidation-v2.md
  sections 6-7.
