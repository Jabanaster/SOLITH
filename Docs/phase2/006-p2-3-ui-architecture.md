# Phase 2 P2-3 — UI Architecture Note

Mission §1: audit existing production UI before designing anything. This is that audit, condensed, plus the resulting design decisions.

## What already exists (audit findings)

- **Main surface**: `src/app/pages/LiveMemoryTrainerPage.tsx` (1267 lines) — plain React hooks (`useState`/`useEffect`/`useCallback`), no context/Redux/Zustand. Talks to the main process only via `window.electronAPI`. Sub-features are split into sibling panel components imported into this page (`AddressDataResearchPanel`, `LiveCorrelationWatcherPanel`, `LiveToggleCardsPanel`).
- **Panel convention**: self-contained panels (`AddressDataResearchPanel.tsx`) take a small prop surface (`{ attached: boolean; ... }`) and own `const api = window.electronAPI` plus their own `useState` internally, rather than lifting all state to the parent. `PointerMapPanel` follows this, not the "fully lifted state + callback props" pattern used by `LiveCorrelationWatcherPanel` (that panel's state genuinely lives in the parent for cross-panel correlation reasons that don't apply here).
- **Existing pointer UI**: `LiveMemoryTrainerPage.tsx:913-974`, the pre-P2-2 single `pointerScan` results list — a flat `<ul>`, one `<li>` per full candidate chain, addresses formatted inline as `` `0x${n.toString(16)}` ``. No tree, no grouping, no map concept (it's a single-target, non-persistent scratch list). Superseded for the map workflow but the flat-list-of-chains rendering idiom is reused for the per-node chain display below.
- **Tree/list primitives**: none. `VirtualCatalogGrid.tsx` is a virtualized *grid* (fixed-size cards, `getKey`/`renderItem`), not a row/tree component, and doesn't fit a variable-height grouped-by-target/chain-step layout. No collapsible-row or indentation-tree component exists anywhere in the repo.
- **Graph/canvas libraries**: none installed (`package.json` has no d3/react-flow/cytoscape/vis-network/konva). Per mission §1 ("do NOT introduce a graph library unless current dependencies are insufficient"): a pointer map is a shallow forest (≤8 targets × ≤10 nodes × depth ≤ a handful of offsets, capped at 200 nodes total) — a plain nested-list/tree rendering in HTML covers this without a canvas/graph dependency.
- **Styling**: mixed CSS Modules + two global stylesheets. Design tokens (`--safe`/`--caution`/`--risky`/`--purple`/`--teal`, `--radius-*`, `--font-mono`, etc.) live in `src/app/styles/index.css:59-126`. The existing `v2-*` classes used by `LiveMemoryTrainerPage` have **no CSS rules anywhere** — that page currently renders unstyled beyond browser defaults and the global `.btn-primary`/`.btn-secondary`. New pointer-map UI gets its own real CSS Module (`PointerMapPanel.module.css`) rather than adding to the unstyled `v2-*` family.
- **Status badges**: a real, working convention — `.badge` + `.badge-risk-safe`/`-caution`/`-risky`/`-blocked` (`index.css:1889-1907`), driven by a `STATE_CONFIG: Record<State, {label, color, explanation}>` map per feature (`TrainerCard.tsx:18-28`). Reused directly for pointer-map node status and completeness state.
- **Context menus**: none exist anywhere in the codebase. Not introduced here — row actions use visible buttons instead (matches every other list in the app).
- **Selection state**: `useState<string | null>(selectedId)` + click-to-toggle + derived `selectedItem = items.find(...)`, paired with a details panel (`TrainerPage.tsx` + `ContextPanel.tsx`). Reused for "select a candidate to inspect its full chain" (mission §9).
- **Keyboard navigation**: no arrow-key/listbox pattern exists anywhere in the app; rows are plain clickable elements. Not invented net-new here — buttons/rows get real `tabIndex`/focus styles (mission §14) but no roving-tabindex listbox, consistent with the rest of the app.
- **Address formatting**: no shared helper exists; every call site inlines `` `0x${n.toString(16)}` ``. `pointerMapNodeChainSteps` (P2-1, `src/core/live-memory/pointer-map.ts:164`) already does this for the *core* `PointerMapNode` shape server-side. The renderer only ever sees the wire DTO (`PointerMapNodeDto`, `moduleOffset` already a `"0x…"` string), so a small DTO-side port (`pointerMapDtoNodeChainSteps`, see below) is needed — same semantics, adapted input shape, not new logic.
- **Delete confirmation**: `window.confirm(message)` everywhere (`Recipes.tsx:70`, `TrainerLibraryPage.tsx:901,1009,1114`, etc.) — no custom modal component for deletes specifically. Reused as-is for "delete map."
- **Renderer tests**: no React Testing Library / DOM rendering anywhere in this repo's test suite. The convention (`tests/virtual-catalog-grid-columns.test.ts`, `tests/process-picker.test.ts`) is to extract pure, exported helper functions from the `.tsx`/`.ts` source and unit-test those with `node:test` via the `scripts/run-node-tests.mjs` wrapper — no component is ever actually rendered in CI. Followed exactly: all non-trivial logic (grouping, filtering, sorting, badge-variant mapping, chain-step formatting) lives in a plain `.ts` module, not inline in the component, so it can be unit-tested the way this repo already tests UI-adjacent logic.

## Design decisions

1. **New pure-logic module**: `src/app/live-memory/pointer-map-ui.ts` — no React, no IPC, fully unit-testable. Owns: `pointerMapDtoNodeChainSteps` (chain-step formatting, ported from P2-1's `pointerMapNodeChainSteps` for the wire DTO shape), `nodeStatusBadge`/`completenessBadge` (status → `{label, variant}` using the existing `badge-risk-*` vocabulary), `isStaleReloadedNode` (distinguishes "never resolved" from "was resolved once, now unresolved after a reload" per mission §5/§10 — the same distinction P2-2's `toInactiveOnLoad` already encodes at the data layer), `groupNodesByTarget`, `filterNodes`, `sortNodes`.
2. **New component**: `src/app/components/PointerMapPanel.tsx` + `PointerMapPanel.module.css`, following the `AddressDataResearchPanel` convention (`{ attached: boolean }` prop, owns `window.electronAPI` + its own state). Imported into `LiveMemoryTrainerPage.tsx` as a new attached-only section, next to the existing single-target Pointer Path Discovery section (not replacing it — that flat scan-list stays for quick one-off lookups; the map panel is the persistent, multi-target, named-collection workflow).
3. **Hierarchy**: Map selector/header → target groups → candidate nodes → (on selection) a chain-step detail list. No graph library. No virtualization library added; the 200-node map cap (P2-2 `MAX_NODES_PER_MAP`) keeps a plain DOM list within normal render budgets, and there is no existing tree-virtualization primitive to reuse (`VirtualCatalogGrid` doesn't fit this shape — see audit above). Large-map UX is exercised via the pure grouping/filtering helpers at 1/10/50/100/200-node fixtures, not via a DOM benchmark this repo has no tooling for.
4. **All map CRUD goes through the preload IPC methods already shipped in P2-2** (`pointerMapCreate/List/Get/Rename/Delete/ScanTarget(s)/Resolve/Refresh/AddNode/RemoveNode/Save/Load/ListSaved/DeleteSaved`) — zero renderer-side reimplementation of map/service logic, per mission §7's explicit prohibition.
5. **No intermediate addresses invented**: `PointerMapNodeDto`/`pointerMapNodeChainSteps` do not carry intermediate dereference addresses (only the final `lastResolvedAddress`), so the UI shows offsets/module-relative steps plus the final resolved address only — never a fabricated intermediate value, per mission §9.
6. **Cancellation — no fake "Cancel" button.** `LiveMemorySession.pointerMapScanTargets` (`src/core/live-memory/live-memory-session.ts:1321`) and everything beneath it (`scanTargetsIntoMap`, `scanForPointerPath`) run **synchronously to completion inside one `ipcMain.handle` call** — unlike the byte-level value scanner, which genuinely needs `startExactScanOperation`/`cancelScanOperation`/`getScanOperationStatus`'s async-operation-with-polling pattern because it can run for a long time over gigabytes of process memory, a bounded BFS pointer scan (capped by `maxDepth`/`maxCandidatesPerLevel`/`maxResults`/`maxTotalScans`/`MAX_TARGETS_PER_SCAN`) has no in-flight window an IPC call could observe or interrupt — the whole operation finishes before the renderer's `await` ever resolves. Adding an operation-ID/poll/cancel wrapper around a call that is already finished by the time anything could poll it would be exactly the "hidden developer API as the user workflow" anti-pattern mission §8 itself warns against, just wearing cancellation's clothing. So P2-3 does **not** add a "Cancel scan" button. What *is* real and is implemented: (a) the scan trigger is disabled while a call is in flight (`busy` state), preventing overlapping scans; (b) if a target's outcome ever does carry `completeness.state === 'cancelled'` (the orchestration layer's between-target abort path, exercised today by `pointer-map-orchestration.test.ts` with a pre-aborted signal — reachable in production if a future caller passes one), the UI renders it with the same truthful "Cancelled" badge as any other incomplete state, never as a plain success. This is a scope finding, recorded honestly rather than covered up with fabricated interactivity.
