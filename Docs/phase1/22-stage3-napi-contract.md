## Kept thin (mission §3.13's explicit requirement)

Every line of Stage 3's napi addition is one of: a type-string parse (`primitive_type_from_str`, `alignment_from_str`), a value-duality conversion (`primitive_value_from_js`, `scan_match_to_js`), or a direct delegation into `solith_scanner_core::exact_scan::scan_exact`. **No scan algorithm, comparison logic, or completeness rule is duplicated or reimplemented in this crate** — `ExactScanTask::compute()` is an 8-line function whose entire body is a `scan_exact(...)` call plus a progress-callback closure identical in shape to Stage 2's `ReadRegionTask`.

## Async execution / non-blocking event loop (mission §3.13)

`ExactScanTask` implements the same `Task` trait pattern Stage 2 established (`compute()` on napi's worker-thread pool, `resolve()` back on the JS thread) — no new async mechanism was introduced; Stage 3 reuses Stage 2's proven approach rather than inventing a second one. Real, executed proof (napi test `readRegionChunked (real async native operation)`'s Stage 2 precedent, and Stage 3's own cancellation/progress tests below) confirms the event loop is never blocked for the scan's duration.

## Cancellation / progress polling (mission §3.13)

Both reuse Stage 2's `ScanCancellationHandle`/`ScanProgressHandle` classes **unchanged** — `scanExact` takes the same cancellation-handle and progress-handle parameters `readRegionChunked` does, and they behave identically (poll-based progress, cooperative between-chunk cancellation). This is deliberate reuse, not a coincidence of similar design: one cancellation/progress model serves every scan operation this crate exposes, present and future.

Real, executed proof: `exact scan: cancellation works from real JS` (polls `progress.snapshot()` until real progress is observed, then cancels, then asserts `completeness.state === 'cancelled'`) and `exact scan: progress works and reflects real work done` (asserts the final polled snapshot's `chunksRead` matches the resolved outcome's own metrics exactly).

## BigInt safety (mission §3.13)

- **Addresses**: every `JsRegion.baseAddress`/`JsScanMatch.address` is `BigInt`, unchanged from Stage 2's contract.
- **i64/u64 values**: `JsScanMatch.valueBigint` is real `BigInt`, proven exact for `u64::MAX` and other beyond-safe-integer values (`u64_beyond_js_safe_integer_round_trips_exactly` in both the Rust suite and, independently, the real napi JS suite via `exact scan: u64 beyond JS safe integer round-trips exactly via BigInt`, which additionally asserts `hit.valueNumber === undefined` — proving the duality contract's other half is enforced too, not just that the value happens to also be readable as a Number somewhere).

## Bounded result retrieval / completeness status / error details (mission §3.13)

- **Bounded results**: `maxResults` (a `bigint` parameter, converted via the same `BigInt::get_u64()` pattern Stage 2 established) — see doc 21 for why this is the chosen bounding mechanism.
- **Completeness status**: `JsExactScanOutcome.completeness` reuses Stage 2's `JsCompleteness` shape unchanged (`state`/`atByte`/`skipped`/`failedReason`), now also produced by the exact-scan path (previously only the raw-read path).
- **Error details**: the same `"<stable_error_kind>: <human-readable detail>"` contract Stage 2 established (module doc, `to_napi_err`) — a Stage-3-specific example is `invalid_configuration: overlap_bytes (2) must be >= primitive width - 1 (7) for u64 scans, or a value spanning a chunk boundary would be missed`, a real thrown error a caller can parse for the stable `invalid_configuration` prefix.

## Value contract, restated for the napi layer specifically

`primitive_value_from_js` enforces the number/BigInt duality **as a validation, not a convenience**: calling `scanExact` with `valueBigint` set for an `i32` scan (or `valueNumber` set for a `u64` scan) throws a typed `invalid_configuration` error rather than silently coercing — a caller cannot accidentally lose precision by passing the wrong JS type for a given `primitiveType`.
