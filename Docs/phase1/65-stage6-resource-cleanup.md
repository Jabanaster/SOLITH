# Phase 1 / Stage 6 — Resource Cleanup / RAII Audit

## §6.13 — ownership traced end to end

| Owner | Cleanup mechanism | Double-release / use-after-release safety |
|---|---|---|
| `ProcessHandle` | `impl Drop` unconditionally calls `CloseHandle`. Deliberately not `Clone`/`Copy` — "exactly one owner must be responsible for `CloseHandle`" (its own doc comment). `unsafe impl Send` so it can cross the napi async-task thread boundary. | N/A — ownership makes double-release a compile-time impossibility |
| `ScanSession::close(self)` | By-value consuming method with an empty body — consuming `self` drops `handle` (→ `CloseHandle`) and `candidates` (`Vec` deallocation) via ordinary Rust drop glue, immediately and unconditionally | N/A — consumed by value, cannot be called twice on the same instance |
| `NativeScanTarget` (napi) | `Arc<Mutex<Option<ProcessHandle>>>`; `detach()` sets the `Option` to `None`. No custom `impl Drop` is written for the wrapper itself — RAII still guarantees `CloseHandle` via the inner `ProcessHandle`'s own `Drop` once the `Arc`'s refcount reaches zero | `detach()` documented and tested safe to call more than once (Stage 6, new: `NativeScanTarget: detach is idempotent and a detached target is used cleanly, not accessed unsafely`). Post-detach use: synchronous methods (`enumerateRegions`) throw cleanly; async methods (`readRegionChunked`) reject the returned Promise — proven, not assumed |
| `NativeScanSession` (napi) | Same `Arc<Mutex<Option<CoreScanSession>>>` pattern; `close()` sets `None`. If the JS wrapper is GC'd without an explicit `close()`, napi-rs's generated finalizer runs the struct's ordinary drop glue, releasing the `Arc` (and, if it was the last reference, the inner session/handle) | `close()` documented and tested idempotent (Stage 6, new: `session: close is idempotent and double-init/invalid-mode misuse is rejected predictably` — three consecutive `close()` calls, then a fresh `createUnknownInitial` proving the prior state was genuinely released, not left half-alive). Use-after-close on every mutating method (`refine`, `getResults`, `generationHistory`, `status`) returns a clean `Err`/rejected-Promise via `ok_or_else(session_not_initialized_err)`, never a panic |
| `ScanCancellationHandle` / `ScanProgressHandle` | Plain `Arc<...>`-backed napi objects, released by ordinary GC/drop; no OS resource to leak | N/A — no OS handle involved |
| `SessionSnapshot` file I/O | No open file handle is retained across calls — `save`/`load`/`delete` each open, use, and close a file handle within one function call (`std::fs::write`/`read_to_string`/`remove_file`), never held open between napi calls | N/A |

## Proven, not just designed: repeated-use and forced-GC evidence

- **Repeated scans (no session):** `no_handle_leak_across_many_open_close_cycles` (Stage 2, 500 iterations), `one_hundred_repeated_exact_scans_do_not_leak_handles` and `one_hundred_repeated_aob_scans_do_not_leak_handles` (Stage 6, new, 100 iterations each) — all bound native-process handle-count growth (`GetProcessHandleCount`) against a warmed-up baseline.
- **Repeated sessions:** `repeated_create_refine_close_cycles_do_not_leak_os_handles` (Stage 4, 10 cycles), `fifty_repeated_session_create_refine_close_cycles_do_not_leak_handles` (Stage 6, new, 50 cycles) — same bounded-growth technique.
- **napi-level repeated cycles:** `session: close releases the session and repeated cycles do not leak handles` (5 create/refine/close cycles through the real compiled addon).
- **JS garbage collection:** `session: dropping all JS references without close() still releases native resources under forced GC` (Stage 6, new) — best-effort, honestly scoped: `node --test` does not expose `global.gc` by default, so the test detects this and calls `t.skip(...)` with an explicit message when unavailable (verified both ways: skips cleanly without `--expose-gc`, passes when run with it). Per this mission's own instruction ("If deterministic GC proof is unreliable: document limitation and rely on explicit close + RAII... Do not fake deterministic GC behavior"), the guarantee this crate actually depends on is explicit `close()` + RAII, proven unconditionally by every test above — the GC test is a bonus confirmation, not the load-bearing proof.

## No unbounded retained native buffers

`CandidateStore` is bounded by `SessionResourceLimits` (`max_candidates`, `max_snapshot_bytes`, `max_session_bytes`, `max_generations_retained`), enforced since Stage 4 and unchanged this mission. `SessionSnapshot`'s own size is independently bounded by construction (§6.9/§6.10: no raw candidate data, no per-generation skip-list detail — only stable labels and counts), and a 1 MiB hard ceiling (`MAX_SNAPSHOT_FILE_BYTES`) is enforced on load, before parsing, so an oversized or corrupted file cannot force an unbounded parse attempt.
