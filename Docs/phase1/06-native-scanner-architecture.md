# Phase 1 / Stage 1 — Native Scanner Architecture, Rust Core, Session/Result Model, Completeness Contract, AOB Design

Covers mission sections 1.7 (native architecture decision), 1.8 (Rust scanner core design), 1.10 (result/session architecture), 1.11 (truthful completeness contract), and 1.12 (AOB/pattern design). This is a **design document** — no implementation exists yet, and none is created by Stage 1.

## 1. Native architecture decision (1.7)

### 1.1 Target shape

```
Electron (main process, TypeScript)
        |  typed IPC (electron/live-memory-ipc.ts, preload.ts) — UNCHANGED SHAPE, new capability
        |
LiveMemorySession / MemoryManager (TypeScript orchestration — attach, guard checks,
        |  propose/confirm/rollback policy, consent — KEPT, not reimplemented in Rust)
        |
napi-rs boundary (new)
        |
Rust native scanner core (new crate, e.g. `solith-scanner-core`)
        |
Windows process-memory APIs (OpenProcess/VirtualQueryEx/ReadProcessMemory/WriteProcessMemory)
```

**Scope boundary, deliberately narrow**: only the *scanning and raw memory I/O* primitives move to Rust — region enumeration, chunked reading, type decode/compare, AOB matching, pointer-chain BFS. The **policy layer stays in TypeScript**: attach authorization, online-guard checks, protected-target blocklist, write-consent/propose/confirm/rollback, freeze orchestration, IPC validation. This mirrors the one real precedent already in this codebase (`native/solith-readonly-scanner`, a Rust binary that is *also* scoped to raw read-only memory operations only, with all policy in TypeScript) and avoids re-litigating already-certified, security-sensitive TypeScript logic (protected-target-guard, online-guard, write-policy-gate — all currently tested and CI-green) in a second language.

### 1.2 Why napi-rs (confirms the Step 0.13.5 freeze; this is the concrete design, not a re-decision)

- In-process native addon (unlike `native/solith-readonly-scanner`'s child-process-over-stdio model) — eliminates per-call process-spawn and JSON-serialization overhead, which matters for a scan loop issuing potentially thousands of region reads.
- Native `bigint`/typed-array support in napi-rs's JS bridge is a direct fix for D06 (int64) and the existing `bigint`-for-addresses pattern already established by `MemoryDriver.readPointer` — napi-rs can return `BigInt`/`ArrayBuffer` natively without the `Number()` coercion that causes D06 today.
- Rust's `Result<T, E>` and enum types map cleanly onto the "truthful completeness" state model (§4 below) — a Rust enum forces every call site to handle every completion state, which the current TypeScript `boolean truncated` flag structurally cannot (it's exactly why five sibling functions silently omit setting it — a `boolean` is too weak a contract).
- `windows-sys` (already a dependency of `native/solith-readonly-scanner`) gives direct, safe-wrapped access to `OpenProcess`/`VirtualQueryEx`/`ReadProcessMemory`/`WriteProcessMemory` without depending on memoryjs's C++ addon at all for the new scanner path.

### 1.3 Crate / addon structure

```
native/solith-scanner-core/          (new Rust crate, napi-rs cdylib)
  Cargo.toml                          napi, napi-derive, windows-sys deps
  src/
    lib.rs                            napi-rs #[napi] exported surface (thin — validates args, delegates)
    process.rs                        ProcessHandle (RAII), attach/detach, identity queries
    regions.rs                        region enumeration + readability/writability classification
    reader.rs                         chunked reader (overlap-aware), read-error classification
    types.rs                          canonical scanner primitive type enum + encode/decode
    scan/
      mod.rs                          scan session state machine, dispatch by mode
      exact.rs, unknown.rs, refine.rs one module per scan-mode family (§ scan-semantics doc 07)
      comparison.rs                   typed comparison evaluation (replaces matchesComparison)
    aob/
      mod.rs                          pattern parse + match (replaces aob-resolver.ts + signature-engine.ts)
      wildcard.rs
    pointer/
      mod.rs                          BFS pointer-chain scan (replaces pointer-scanner.ts)
    session.rs                        ScanSession struct (§3 below), cancellation token, progress channel
    completeness.rs                   the completion-state enum (§4 below), shared by every module above
  index.d.ts                          generated by napi-rs build (typed JS surface)
```

One crate, not several — the existing `native/solith-readonly-scanner` precedent is a separate binary for a genuinely separate concern (read-only pointer-chain *validation*, no scanning); the new interactive scanner core is one cohesive unit and should not be artificially split.

### 1.4 Ownership, handle lifetime, threading

- `ProcessHandle` is an RAII Rust struct (mirrors `native/solith-readonly-scanner/src/main.rs`'s existing `ProcessHandle` exactly — same pattern, proven in this codebase already) — `Drop` calls `CloseHandle` unconditionally, so a panic or early return can never leak a handle.
- One `ProcessHandle` per `LiveMemorySession` attach, matching current TypeScript session lifetime 1:1 — no handle pooling, no cross-session sharing (mirrors current design, which is correct: SOLITH is explicitly single-target, local, single-player scope per `types.ts`'s own header comment).
- **Threading model**: scans run on napi-rs's `AsyncTask`/threadsafe-function worker pool (one logical worker per in-flight scan), never on the Node.js main thread — this is what makes cancellation and progress reporting possible at all (today's synchronous, single-threaded JS scan loop cannot be interrupted mid-region). A `LiveMemorySession` should permit **at most one in-flight scan at a time** per session (explicit mutex/state flag in `session.rs`), rejecting a second concurrent scan request with a clear "scan already in progress" error rather than allowing interleaving — closes the concurrent-scan-race category from the mission's defect-hunt list (1.4) before it can ever be built into the new core.
- Region reads within one scan may be parallelized across the worker pool (read N regions concurrently, bounded by a configurable worker count) as a Phase 1 *stretch* optimization — not required for correctness, and must never be allowed to reorder result delivery in a way that makes output nondeterministic run-to-run for the same real memory state (see doc 03 additional-defect item on ordering nondeterminism).

### 1.5 Cancellation token

- A `CancellationToken` (Rust `Arc<AtomicBool>` or napi-rs's native abort-signal integration) is created per scan session and exposed to TypeScript as an opaque handle returned from the "start scan" call.
- The Rust scan loop checks the token **between every region read** (not just at the top of the function) — this bounds cancellation latency to "at most one region's read+decode time," which doc 04's baseline shows is small for `scanFirst`-class scans (sub-millisecond per region at realistic sizes) and bounded even for the slowest primitive measured (`scanForPointerPath`, ~59ms per 8 MiB region in the JS baseline — the Rust equivalent should be materially faster).
- IPC surface: `live-memory-scan-cancel(sessionScanId)` — new channel, additive to the existing IPC set (no existing channel's shape changes).

### 1.6 Progress callbacks

- A threadsafe-function callback fires after each region (or, for large single regions, after each chunk — see §2.2) with `{ bytesScanned, bytesTotal, regionsScanned, regionsTotal, matchesSoFar }`. `bytesTotal`/`regionsTotal` are computed from the pre-enumerated region list at scan start, so percent-complete is always `bytesScanned / bytesTotal`, monotonically non-decreasing, and mathematically bounded to `[0, 100]` — this directly satisfies the exit-gate requirement "no false complete states" / "progress exceeding 100%" by construction rather than by convention.
- IPC surface: a new `live-memory-scan-progress` push event (main → renderer), additive.

### 1.7 Scan-session representation

See §3 (Result/Session Architecture) below — this is the same object.

### 1.8 Result representation / BigInt / JS boundary batching

- Every address crosses the napi-rs boundary as a native `BigInt` (napi-rs supports this directly) — never a `Number`, closing the address-precision half of D06 the same way `readPointer` already does today for pointers specifically; the new core generalizes that pattern to *every* 64-bit quantity (addresses **and** int64/uint64 *values*).
- Scanned **values** for `int64`/`uint64` types are also returned as `BigInt`, not `Number` — this is the actual fix for D06's value-precision-loss half, which `readPointer`'s existing pattern does not cover (it only fixes addresses). `ScanMatch.value`'s TypeScript type must become `number | bigint` (discriminated by `dataType`), a deliberate, visible breaking change to the current all-`number` `ScanMatch` shape — flagged here explicitly per the mission's "if a production change seems necessary... STOP and report" instruction: **this is a necessary, foreseen breaking type change for Phase 2+ implementation, not something Stage 1 is doing now; recorded here so Stage 2 planning does not treat it as a surprise.**
- Large result sets are **batched across the IPC boundary** — the napi-rs layer streams matches in fixed-size pages (e.g. 500 at a time) via the progress-callback channel rather than materializing all 10,000 max-matches in one native→JS marshal, addressing the "IPC payload explosion" category from the mission's additional-defect-hunt list.

### 1.9 Zero-copy opportunities / buffers

- Region bytes read by Rust for decode/compare purposes **never need to cross the FFI boundary as raw bytes** — decoding and comparison happen entirely in Rust; only typed match results (address + value + dataType) cross over. This is a structural win over the current TypeScript design, which must materialize a full `Buffer` for every region in JS just to decode it.
- The one legitimate zero-copy candidate is `scanFirstUnknown`'s baseline-snapshot retention (today: `Buffer.from(buf)` copies held in a JS `Map`, up to 512 MiB) — in the new design this baseline lives entirely in Rust-owned memory for the session's lifetime, exposed to TypeScript only as an opaque snapshot handle, never copied into the JS heap at all. This removes the "does the JS heap balloon with baseline copies" concern (mission's memory-leak defect-hunt category) by construction.

### 1.10 Memory safety / error model

- All raw pointer arithmetic is confined to `regions.rs`/`reader.rs`, behind a safe API; `unsafe` blocks are limited to the actual `ReadProcessMemory`/`WriteProcessMemory`/`VirtualQueryEx` FFI calls themselves (same pattern `native/solith-readonly-scanner/src/main.rs` already uses successfully).
- Every fallible operation returns `Result<T, ScanError>`, where `ScanError` is a closed enum (`ProcessExited`, `RegionUnreadable{address, size}`, `AccessDenied`, `InvalidAddress`, `HandleInvalidated`, ...) — this is what makes the completeness contract (§4) enforceable: Rust's exhaustive `match` means a new error variant cannot be silently ignored the way a JS `catch { continue; }` can.
- napi-rs surfaces `Result::Err` as a rejected Promise with a structured error object (`{ code, message, address? }`), not a generic string — TypeScript call sites get a typed error to branch on instead of parsing an error message string.

### 1.11 Stale-process protection

- The Rust `ProcessHandle` records the same identity triple the TypeScript layer already captures at attach (`executablePath`, `startTime`, `volumeSerial`/`fileIndex` — see `windows-process-identity.ts`, kept in TypeScript, unchanged) — the Rust core itself does not re-derive identity (that stays a TypeScript/PowerShell responsibility, since it is not performance-sensitive and is already correct/tested).
- Before *starting* a scan, the Rust core re-validates that its own held `ProcessHandle` is still valid via a lightweight `GetExitCodeProcess`/`STILL_ACTIVE` check — if the process has exited, the scan fails fast with `ScanError::ProcessExited` rather than reading garbage from a stale handle or an OS-recycled PID's unrelated new process.

### 1.12 Architecture / packaging / build

- **Windows-only conditional build**: the new crate's `napi-rs` binding is compiled only for the `x86_64-pc-windows-msvc` target (matching this project's existing Windows-only scope — `process/index.ts`'s mac/Linux fallback is for the *unrelated* `isGameRunning` liveness check, not the scanner). Non-Windows CI jobs (if any exist) skip building/loading this addon entirely, mirroring how `native-memory-driver.ts` already treats `memoryjs` as an optional, lazily-loaded dependency.
- **Electron native module loading / ABI compatibility**: napi-rs addons need `electron-rebuild` (or napi-rs's own Electron target support) against the exact Electron ABI, the same requirement `memoryjs` already has today (`native-memory-driver.ts`'s own doc comment: "Run `npx electron-rebuild` for the packaged app"). No new class of build risk is introduced — it is the same category of risk this codebase already manages for `memoryjs`.
- **Rebuild requirements / fresh-clone behavior**: `native/solith-readonly-scanner` already establishes the precedent of a native artifact checked into the tree partially pre-built (`target/release/*.exe` committed) — the new crate should instead follow **the opposite, safer pattern**: build from source in CI and on `npm install` (via a `postinstall` step or an explicit `npm run build:native` step documented in `README.md`), never committing a pre-built `.node` binary, since a `.node` addon (unlike a standalone `.exe`) must exactly match the consuming Node/Electron ABI or it fails to load at all — committing one risks exactly the kind of "works on my machine, fails on fresh clone" class of bug the mission explicitly asks Stage 1 to design against.
- **CI build strategy**: add a native-build CI step (Rust toolchain + `napi build --release`) before the existing `npm test`/`Windows native and Electron gate` jobs, so a native-build failure is caught as its own distinct, clearly-labeled CI failure rather than manifesting as a confusing downstream test failure.

## 2. Rust scanner core design (1.8)

### 2.1 Region enumeration

- One Rust function, `enumerate_regions(handle) -> Vec<Region>`, called once per scan (not per chunk) — this is the single source of truth for "what regions exist right now," replacing the informal duplication between `native-memory-driver.ts`'s deny-list readability check and `native/solith-readonly-scanner`'s allow-list (doc 01 §4/§18 finding #4). The new core defines **one** canonical readability policy, expressed as an explicit allow-list (clearer to audit than a deny-list, since an allow-list fails safe against an unrecognized future `PAGE_*` flag combination, whereas a deny-list fails unsafe by defaulting to "readable").
- `Region { base: u64, size: u64, protection: ProtectionFlags, kind: RegionKind }` — `RegionKind` is a new, explicit `enum { Image, Private, Mapped, Unknown }` derived from `MEMORY_BASIC_INFORMATION.Type`, which **no current implementation reads at all** (doc 01 §4) — this closes that gap by construction and gives the exit-gate's "writable/executable/read-only region filters" capability (doc 05) a real, queryable dimension beyond just writable/not.

### 2.2 Chunked reading with overlap

- Configurable `chunk_size` (default candidate: 1 MiB, matching the one real Windows `ReadProcessMemory` per-call cost/reliability sweet spot already implicitly assumed by the existing 1 MiB cap — but now a *deliberate, chunked-continuation* boundary, not a silent hard stop).
- A region larger than `chunk_size` is read in successive chunks, **each chunk overlapping the previous by `max_value_width - 1` bytes** (7 bytes, since the widest scan primitive is 8 bytes) for value/comparison scans, or by `pattern_length - 1` bytes for AOB scans — this is the concrete mechanism that makes "a value/pattern spanning a chunk boundary" (an explicit mission concern, 1.8 and 1.4) provably unmissable: the overlap window guarantees every possible aligned starting offset is fully contained in at least one chunk.
- A chunk read that fails (region partially unmapped mid-read, access denied) marks that chunk's byte range as `RegionUnreadable` in the session's completeness record (§4) and continues with the next chunk — never aborts the whole region, and never silently drops the failure the way today's `catch { continue; }` does.
- **This directly retires the 1 MiB read cap as a correctness limitation** (D02): the cap becomes an internal chunk-size tuning knob, invisible to scan completeness, instead of a silent data-loss boundary.

### 2.3 Alignment

- Default: **unaligned-safe** for every scan mode — the comparator checks every byte offset within a chunk (`offset += 1`), not `offset += valueSize(dataType)`, unless the caller explicitly opts into an aligned-fast-path.
- Optional `AlignmentMode::Aligned(width)` fast path (opt-in, documented, never silent) trades completeness for speed on processes/games known to only store values at natural alignment — this is a genuine optimization opportunity doc 04's baseline suggests is worth having (unaligned scanning is inherently more expensive: up to N× more candidate offsets to decode for an N-byte type), but it must never be the default, per the mission's explicit instruction ("never silent correctness loss").
- This is a **behavior change** from today's scanner, which already only steps by the selected type's own width (never a hardcoded 4 — confirmed absent in doc 02) but has never scanned genuinely unaligned data either. The new default (byte-stepping) is strictly more complete; the exit gate's "unaligned values proven" requirement (doc 10) is written against this new default, not the current behavior.

### 2.4 Canonical primitive type system

```rust
enum ScanType {
    I8, U8, I16, U16, I32, U32, I64, U64,
    F32, F64,
    Utf8 { max_len: u32 }, Utf16 { max_len: u32 },
    Bytes { len: u32 },
    Aob { pattern: Vec<Option<u8>> }, // None = wildcard byte
}
enum ScanValue {
    Int(i64), UInt(u64), Float(f64),  // widened internally; UInt(u64) covers the full unsigned range losslessly
    Str(String), Bytes(Vec<u8>),
}
```
- `UInt(u64)`/`Int(i64)` are the internal widened representations; the **JS boundary representation for `I64`/`U64`-typed values is always `BigInt`** (§1.8), never widened-then-narrowed through a JS `Number` — this is what actually closes D06, as opposed to today's `Number(BigInt)` coercion.
- Full i8–i64/u8–u64/f32/f64 matrix closes the CE gap matrix's "multiple primitive types" row (doc 05) — narrower types (i8/u8/i16/u16) that don't exist in today's `LiveValueType` at all become first-class.
- `Utf8`/`Utf16` string scan and `Bytes` fixed-length scan are genuinely new capability (doc 05: "string scans — absent"), not a port of existing logic.

## 3. Result / session architecture (1.10)

```rust
struct ScanSession {
    scan_id: Uuid,
    process: ProcessIdentity,       // pid, exe path, start time, volume serial/file index — mirrors LiveProcessTarget
    executable_identity: ExeIdentity, // sha256 at attach time, for cross-restart pointer-path stability checks
    scan_type: ScanType,
    mode: ScanMode,                 // Exact | UnknownInitial | Changed | Unchanged | Increased | Decreased
                                     // | IncreasedBy | DecreasedBy | Between   (formal semantics: doc 07)
    region_policy: RegionPolicy,    // writable/readonly/executable/image/private/mapped filters (§2.1)
    alignment_mode: AlignmentMode,  // §2.3
    candidates: CandidateStore,     // see below — never "every address as a JS object"
    baseline: Option<UnknownScanBaseline>, // Rust-owned raw bytes for unknown-initial scans (§1.9), never copied to JS
    progress: ProgressState,        // bytesScanned/bytesTotal/regionsScanned/regionsTotal/matchesSoFar
    cancellation: CancellationToken,
    completeness: CompletenessRecord, // §4 — the actual truth ledger
    created_at: Instant,
    metrics: ScanMetrics,           // bytesRead, regionsRead, chunksRead, wallClockMs — feeds doc 04-style baselines going forward
}
```

- **Candidate storage** (per mission 1.9's storage-design concern for unknown-initial scans, which can be enormous): a plain `Vec<Match>` is adequate for exact/refinement scans bounded by `maxMatches` (kept, same 10,000 default as today unless evidence justifies changing it), but the **unknown-initial baseline** is stored as raw region byte copies inside Rust (not one JS object per candidate — today's design already avoids this at the JS layer via `UnknownScanSnapshot`, and the new design keeps that discipline, just moved into Rust-owned memory instead of a JS `Buffer` copy). A future optimization (bitmap/compressed candidate set for a post-first-narrowing candidate list) is **not required for Phase 1 exit** — flagged as a documented future improvement, not a blocking design gap, since doc 04's baseline shows the JS-side cost of the current `Vec`-like approach (`ScanMatch[]`) is not the bottleneck (region-read count is).
- **A stale process/session must not silently remain valid after restart** (explicit mission requirement, 1.10): `ScanSession.process`/`executable_identity` are captured once at attach and re-validated (§1.11) before every scan start; a `LiveMemorySession` (TypeScript) that detects a PID-reuse/identity mismatch (already-implemented, tested logic in `windows-process-identity.ts` — kept, not reimplemented) must invalidate/drop any `ScanSession` handle it holds for the old identity rather than allowing a new scan to run against a stale Rust-side handle.
- Result representation for a single match: `{ address: BigInt, value: number | BigInt | string, dataType: ScanType, regionKind: RegionKind }` — the `regionKind` tag is new (§2.1) and lets the UI show/filter by image/private/mapped without a second round-trip.

## 4. Truthful completeness contract (1.11) — mandatory

Replacing the current single `truncated: boolean` (inconsistently set — D01/D05) with an explicit, exhaustive completion-state enum:

```rust
enum ScanCompleteness {
    Complete,
    CompleteWithSkippedRegions { skipped: Vec<SkippedRegion> }, // each: {address, size, reason}
    Cancelled { at_byte: u64, at_region_index: u32 },
    ProcessExited { at_byte: u64 },
    ReadErrorLimit { errors: Vec<ReadError> },     // too many individual read failures to continue safely
    ResourceLimit { limit: ResourceLimitKind, at_byte: u64 }, // maxTotalBytes / maxMatches / chunk-budget hit
    Failed { reason: String },
}
```

Rules, enforced structurally (not by convention) because Rust's `match` is exhaustive:

1. **Every scan result carries exactly one `ScanCompleteness` value** — there is no code path that can return match data without also returning a completeness value, because `ScanResult { matches: Vec<Match>, completeness: ScanCompleteness, metrics: ScanMetrics }` is the *only* return type every scan function produces (compare to today, where `bigint | null` for AOB carries no completeness concept whatsoever — D04).
2. **`Complete` is only ever returned when literally every region in the enumerated, policy-filtered region list was fully read and compared** — not "no error was thrown," which is today's implicit (and wrong) definition.
3. **`CompleteWithSkippedRegions` is the honest replacement for today's silent per-region `catch { continue; }`** — every skipped region is named (address, size, and *why*: unreadable, freed-mid-scan, exceeded a byte budget), so a caller (and eventually the UI) can show the user exactly what was not covered, rather than a bare boolean.
4. **A caller must be able to answer, from the returned value alone**: what was scanned (region list + completeness), what was not (`skipped` list), why (each `SkippedRegion.reason` / the completeness variant itself), whether the match list is complete (`Complete` vs. anything else), and — the mission's explicit requirement — **AOB "not found" must never mean "not found" if required memory was not actually scanned**: an AOB scan function's return type becomes `{ matches: Vec<Address>, completeness: ScanCompleteness }`, so `matches.is_empty()` and `completeness != Complete` are two independently observable facts, and the TypeScript layer's UI copy is written to check both (e.g. "no matches found in the region(s) actually scanned — N regions totaling M bytes were skipped; see details" instead of a bare "not found").
5. **IPC surface change**: every scan-result IPC response shape gains a `completeness` field (structured, not boolean) alongside `matches`. This is the same kind of foreseen, deliberate breaking change flagged in §1.8 — recorded here for Stage 2 planning, not implemented now.

## 5. AOB / pattern architecture (1.12)

- **Native SOLITH scanner owns interactive AOB semantics** — a single canonical implementation in `native/solith-scanner-core/src/aob/`, replacing all three of today's live-scanner-adjacent implementations (`aob-resolver.ts`, `signature-engine.ts`'s exact-match path, and the informal duplication between them — doc 01 §11 #1/#2). `signature-engine.ts`'s **fuzzy/drift-tolerant matching** (Hamming/edit-distance, `hintAddress`-scoped search) is a genuinely distinct capability (patch-resilience for already-known signatures, not general scanning) and is **kept as a TypeScript-level feature that calls into the new native exact-match primitive for its inner search step**, rather than being ported wholesale — no evidence suggests its fuzzy-matching logic itself is a bottleneck (doc 04 did not benchmark it directly; it is not part of the interactive first-scan hot path).
- Requirements, all closing specific gaps identified in doc 01/02:
  - Wildcards (`?`) — kept, same token semantics as today.
  - **Nibble wildcards** (`?A`/`A?`-style half-byte wildcards) — genuinely new; needed if/when CT corpus signatures using nibble wildcards are found during Phase 1's real-CT-corpus validation (120,245 AOB signatures already parsed and available per ROADMAP.md's CT-ingest certification — Phase 1 should sample this corpus for nibble-wildcard usage before committing engineering effort here, rather than building it speculatively; recorded as a **design contingency**, not a hard Stage 1 requirement).
  - Exact bytes — kept.
  - Chunk overlap — inherits §2.2's general mechanism; an AOB pattern of length P uses a `P-1`-byte chunk overlap.
  - Region boundaries — same chunked-reader mechanism as value scans; no separate AOB-specific region logic.
  - Module filters / executable/readable filters — kept from `aob-resolver.ts`'s existing `moduleName` option and `RegionPolicy` (§2.1/§3), extended with the new `RegionKind` dimension.
  - All matches / first match — today's `scanAobInProcess` returns only the first match (`return` on first hit, `aob-resolver.ts:95`); the new core supports both an "all matches" mode (bounded by `maxMatches`, same discipline as value scans) and an explicit "first match" mode for callers that only need one (e.g. `feature-resolver.ts`'s AOB-then-pointer-fallback resolution, which only ever needs a single hit) — this is a genuine capability addition, not a behavior change to the existing single-match callers.
  - Cancellation / progress — inherits §1.5/§1.6 uniformly; AOB scanning gets the same cancellation/progress support as value scanning, which it has **zero** of today.
  - Truthful incompleteness — inherits §4 uniformly; this alone closes D04.
- **Vectorscan remains specialist for high-volume compatible pattern batches** — i.e., bulk CT-corpus-scale signature *validation/repair* work (the existing `src/core/runtime/aob-repair-analyzer.ts` use case, already separate from the interactive scanner) is a candidate for a Vectorscan-backed batch matcher in a later phase, evaluated on its own merits against real corpus-scale throughput needs. The interactive, single-target, single-session live scanner described in this document does **not** depend on Vectorscan and must not have its semantics distorted to fit Vectorscan's batch-oriented API shape, per the mission's explicit instruction.

## Summary for the FINAL RESPONSE

- **NATIVE ARCHITECTURE**: Electron/TS orchestration (attach, policy, consent) unchanged; new napi-rs boundary; new single Rust crate (`solith-scanner-core`) owns region enumeration, chunked reading, type decode/compare, AOB, and pointer BFS. Windows-only build, CI-built (not committed pre-built), Electron-rebuild-compatible.
- **NAPI-RS ROLE**: in-process (not child-process) FFI boundary; native BigInt for addresses and 64-bit values; async worker-pool execution enabling real cancellation/progress; typed `Result`-based error surface.
- **RUST CORE**: chunked region reader with type/pattern-width-aware overlap (closes D02/D04's silent-cap class structurally); default unaligned-safe scanning with an explicit opt-in aligned fast path; full i8–u64/f32/f64/UTF-8/UTF-16/bytes/AOB type system; native `RegionKind` (image/private/mapped) classification not present in any current implementation.
- **64-BIT REPRESENTATION**: BigInt end-to-end for both addresses (already true today via `readPointer`) and int64/uint64 *values* (not true today — this is the actual D06 fix), eliminating the `Number()` coercion and its documented value-collision failure mode (doc 02).
- **COMPLETENESS CONTRACT**: a closed, Rust-enum-enforced `ScanCompleteness` type (`Complete`/`CompleteWithSkippedRegions`/`Cancelled`/`ProcessExited`/`ReadErrorLimit`/`ResourceLimit`/`Failed`) replaces the current inconsistently-set boolean, returned alongside matches on every scan (including AOB, which has none today) so "not found" and "not fully scanned" are always independently observable.
- **AOB ARCHITECTURE**: one canonical native exact-match engine (replacing 2 of today's 4 parallel implementations), `signature-engine.ts`'s fuzzy/drift matching kept in TypeScript calling into the new native primitive, Vectorscan reserved for a separate future batch/corpus-scale use case.
- **SESSION ARCHITECTURE**: `ScanSession` struct capturing process/executable identity (re-validated pre-scan for stale-process protection), region policy, alignment mode, cancellation token, progress state, completeness record, and metrics — Rust-owned baseline storage for unknown-initial scans (no JS-heap copy).
